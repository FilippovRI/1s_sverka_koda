# typovaya-up — сверка модулей УП с типовой БП (OneScript)

Утилита на языке 1С (OneScript, без базы) сравнивает две файловые выгрузки конфигурации
(Конфигуратор → «Выгрузить конфигурацию в файлы») и строит HTML-разбор модулей `.bsl`:
что совпадает, что отличается косметически, что можно унести в расширение автоматически
(в том числе через синтез хуков `&Перед` / `&После` / `&ИзменениеИКонтроль` / `&Вместо`)
и что требует ручного разбора. При сравнении **модулей** каталоги `\Forms\` и `\Templates\` пропускаются; отдельно — inventory форм (`--анализ-форм`).

## Требования
- OneScript 2.x (проверено на 2.2.0, linux-x64; на Windows — установщик с https://oscript.io или релиз GitHub EvilBeaver/OneScript).
- Сторонних пакетов не нужно: только стандартная библиотека (файлы, XML, JSON, хеширование).

## Запуск
```
oscript src/Главный.os --исходная "D:\Выгрузка УП" --поставщик "D:\выгрузка БП" --настройки "merge.xml" --выход "out"
```
Синонимы: `--source/-и`, `--vendor/-п`, `--settings/-н`, `--out/-в`, `--расширение/--extension/-р` (имя черновика, по умолчанию `УП_Доработки`), `--префикс/--prefix` (по умолчанию `УП_`). Без аргументов — справка, код 1.

- **исходная** — доработанная конфигурация (УП), папка с `Configuration.xml`;
- **поставщик** — типовая конфигурация (БП);
- **настройки** (необязательно) — XML настроек сравнения/объединения Конфигуратора
  (`http://v8.1c.ru/8.3/config/merge/settings`). Из объектов с отмеченными свойствами-модулями
  (`Module`, `ObjectModule`, `ManagerModule`, `CommandModule`, `RecordSetModule`, …) строится периметр.
  Если ни один путь из периметра не найден — сравниваются все общие модули, в лог пишется предупреждение;
- **выход** — папка результата (по умолчанию `out`).

Конфигурации считаются несвязанными: модули сопоставляются по относительному пути
(`CommonModules\Имя\Ext\Module.bsl`, `Documents\Имя\Ext\ObjectModule.bsl`), UUID не используются.

## Результат
- `razbor_moduley.html` — автономная страница (данные JSON внутри). Слева дерево: корзина → тип → модуль → процедуры;
  справа построчное сравнение «Поставщик (БП) | Исходная (УП)» и предлагаемое тело хука.
  Кнопки «Предыдущий/Следующий раздел», «Предыдущая/Следующая процедура»; клавиши ←/→ (H/L) — модули, ↑/↓ (K/J) — процедуры.
  Блок «Что смотреть» объясняет, почему модуль/метод попал в корзину и какой хук предложен.
  Одинаковые модули в HTML не попадают (только их количество).
- `summary.json` — количества и списки путей по корзинам, плюс `hooks` (before/after/changeAndControl/instead/newMethod/none).
- `log.txt` — лог прогона.
- `extension\` — файловая выгрузка черновика расширения (порт `ExtensionDraftWriter` Сверки): `Configuration.xml`
  (Adopted, Name, NamePrefix, Customization, ChildObjects с заимствованными объектами и языком), `{Папка}\{Имя}.xml`
  заимствованных объектов (ExtendedConfigurationObject = uuid объекта из выгрузки УП) и модули с хуками
  (`&Перед`/`&После`/`&ИзменениеИКонтроль`/`&Вместо` + `ПродолжитьВызов();`) и новыми методами, все с префиксом.
  Пишутся все методы с авто-хуком и новые методы, даже из модулей «ручного разбора». Модули команд объектов
  (`{Папка}\{Объект}\Commands\{Команда}\Ext\CommandModule.bsl`) пишутся: команда заимствуется внутри
  `<ChildObjects>` XML объекта (uuid команды берётся из XML объекта УП). Модули корня конфигурации и модули
  только в УП пропускаются (см. log.txt). Подробности и порядок загрузки — `extension\README.txt`.
- `restored\` — тексты модулей УП, где методы с авто-хуком возвращены к типовому тексту, а новые методы удалены
  (переехали в расширение). Для ручной проверки перед заменой модулей основной конфигурации.
  **Не загружайте расширение на нетронутую УП** — доработки выполнятся дважды. Сначала замените модули типовым текстом.
- Папка результата не может лежать внутри входных выгрузок (код 2); входные файлы не изменяются.

Корзины:
| код | смысл |
|---|---|
| identical | файлы совпадают побайтно (или по тексту при другой кодировке) |
| cosmetic | «Отличие без доработки»: только комментарии, пустые строки, отступы |
| auto | «Автоунос»: только новые методы и/или изменённые методы с безопасным хуком (нет удалений и отличий вне процедур) |
| manual | «Ручной разбор»: удалены типовые методы, отличается код вне процедур, или хук не выводится |
| only_source / only_vendor | модуль есть только в одной из выгрузок |

### Синтез хуков
Для каждого изменённого метода сравниваются **тела** (без `Процедура`/`КонецПроцедуры`). Эвристики как в C#-Сверке (`HookSynthesizer`):

1. типовое тело — строгий префикс доработанного → `&После`;
2. типовое — строгий суффикс → `&Перед`;
3. все типовые строки сохранены по порядку, есть вставки → `&ИзменениеИКонтроль` с `#Вставка`;
4. есть `ПродолжитьВызов` → `&Вместо` (вызовы вырезаются из тела);
5. patience-diff / LCS при достаточном общем каркасе → `&ИзменениеИКонтроль` с `#Удаление`/`#Вставка`;
6. иначе при непустом доработанном теле → `&Вместо`;
7. пустое типовое при непустом доработанном → ручной разбор.

Окно LCS больше ~400 000 ячеек в OneScript не строится: участок считается «удалить всё + вставить всё».

Методы: `same` / `changed` (с `hook`, `hookDecision`, `hookBody`) /
`added` (`hook=newMethod`) / `removed`.

Кодировка `.bsl`: UTF-8 (с BOM или без), при битых символах — windows-1251.

## XML черновика (ibcmd 8.5+)

- Заимствованные **Catalog/Document/…** получают `InternalInfo` из XML объекта в выгрузке УП; **CommonModule**, **Language**, **CommonCommand** — без `InternalInfo` и без пустых `ChildObjects`.
- `Configuration.xml` подставляет `extension_meta/Configuration_InternalInfo.xml` (замените на фрагмент из экспорта вашего пустого расширения).
- Формат выгрузки в черновике: `version="2.21"`, `xmlns:pal`.

## Ограничения (не в master или неполно)

- **Есть:** черновик `extension/`, каталог `restored/`, синтез хуков в отчёте — см. раздел «Результат» выше.
- **Нет / частично:** CallRewrite и доказанная подмена вызовов; Excel-периметр подсистем; полный цикл ibcmd import в CI.
- **`--анализ-форм`:** только inventory реквизитов в `Form.xml` (файл `forms_analysis.json`); без `РеквизитФормы`, без правки выгрузок.
- **GUI** (`launcher/`): сборка в репозитории; интерактивный runtime на Windows агентом не проверялся.
- модулей объектов, которые в настройках есть только со стороны поставщика без свойств-модулей
  (например `fullNameInSecondConfiguration` без `<Property>`): в режиме с настройками они не попадают в периметр;
- разбор методов строковый: объявления `Процедура/Функция Имя(` в начале строки, конец — `КонецПроцедуры/КонецФункции`;
  `#Область`, директивы препроцессора и многострочные строки с `//` внутри могут слегка исказить нормализацию.
